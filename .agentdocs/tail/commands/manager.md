## Специфика codemaster

**Мерило required-vs-backlog — инварианты проекта** (ARCHITECTURE §1/§3): never-lie (proof-carrying,
явная неопределённость `unresolved/partial/dynamic`, no silent-truncation), never-hang (дедлайн, no
unbounded loop, no per-call repo-scale работа), строгий лейеринг (downward-only, plugin-DAG,
`common/`→`core/`), файл ≤300 строк, внешние вызовы обёрнуты → `ToolFailure`, boundary-вход
zod-валидирован.

**Добор порождённых задач (§9) в этом репо:** критерий (3) «приоритет оправдывает круг» читается как
`high`+ ЛИБО живая ложь в `main`, про которую мы теперь ЗНАЕМ — never-lie перевешивает размер правки.

**Механический гейт:** `npm run fix-and-check` (EXIT 0) — он же авто-сносит механический dead-code
(не правь руками). Верификацию на мердже гоняй САМ на main: `npm run check` + `npm test`. Точечно —
`node --test test/foo.test.ts` (файл, не директорию).

**Параллельный тест-лок (борьба за CPU между воркерами).** Много worktree на одной машине → два
одновременных полных `npm test` (>1 мин, все ядра) не займут 2×, а трэшат суперлинейно (грызня за
каждое ядро). Machine-wide **мьютекс K=1** сериализует тяжёлые прогоны: helper
`~/.codemaster-orch/with-test-lock.mjs` (атомарный `open('wx')` + steal мёртвого/протухшего холдера +
release на exit/сигналах), вызов `node ~/.codemaster-orch/with-test-lock.mjs -- npm test`. Ты
(менеджер) **провижнишь helper при старте если его нет** (атомарный лок-скрипт на fs), и на мердж-гейте
гоняешь полный сьют/`fix-and-check` через ТОТ ЖЕ лок — одна очередь с воркерами, менеджер и воркеры не
сталкиваются. Лок ещё и выставляет `TEST_CONCURRENCY=ядра−4` (замер: ≈та же wall-time что на max, но
машина не забита под ноль + меньше contention-флака; хвост сьюта wait-bound e2e, не CPU); npm test-скрипты
читают эту env, CI (без лока) гонит на default-max. Замер concurrency — эксперименты выше. В бриф воркеру — **каденция:** таргетные `node --test <файл>` во время итерации БЕЗ лока
(дёшево); полный `npm test` + `fix-and-check` только на DONE ЧЕРЕЗ лок. (K=1, не семафор: полный сьют
и так сатурирует все ядра, даже 2 параллельных трэшат.)

**Полный сьют — дорог; гоняй его РОВНО когда результат мог измениться, не рефлекторно.** Лок сериализует,
но настоящая экономия — сократить ЧИСЛО прогонов (иначе процессор гудит нон-стоп: воркер гоняет в
итерации + на DONE + СНОВА после ребейза + ты на мердже = ×N мусора). Правила:

- **Тест-группы** (сплит по стоимости): `test:light` (unit+golden, ~12с — inner-loop) · `test:heavy`
  (e2e+differential — real-spawn + cold-Program-оракулы, ~90% времени) · `npm test` = всё (авторитет).
  Профиль — `npm run test:timing` → test-timing.html.
- **Воркеру в бриф:** полный `npm test` РОВНО раз на DONE; в итерации — таргетные `node --test` или
  `npm run test:light`;
  после ребейза НЕ перегонять сьют вслепую — при ЧИСТОМ ребейзе поверх disjoint-изменений прежний green
  держится, нужен лишь `fix-and-check` (ловит prettier-дрейф, rebase пропускает хук) + доклад «rebase
  clean». Полный ре-прогон после ребейза — ТОЛЬКО при конфликтах / реальном пересечении.
- **НЕ проси рефлекторный ре-прогон на каждый ребейз** — при чистом disjoint-ребейзе green воркера +
  post-rebase fix-and-check достаточно.
- **ОПТИМИСТИЧНАЯ позиция: ДОВЕРЯЙ DONE-green воркера, полный сьют на main гоняй РЕДКО.** ff-merge
  байт-в-байт равен tip'у, что воркер УЖЕ проверил зелёным на DONE → перепрогон того же кода детерминирован
  = дубль. Каждый трек самопроверяется на DONE и disjoint-by-design → комбинация ломается РЕДКО. Так что
  НЕ гоняй полный `npm test` на каждый мердж и даже не на каждый батч. Гоняй его РЕДКО: в КОНЦЕ волны (раз
  на серию мерджей — тестит комбинированный main, что никто целиком не покрыл), либо по «запаху»
  (flaky-чувствительная зона, странный вывод, shared-runtime seam). В промежутке — доверяй green воркера.
- **Дешёвая страховка, которую ОСТАВЛЯЕМ:** воркер после ребейза гонит `fix-and-check` (tsc+lint+prettier,
  ~секунды, НЕ сьют) на комбинированном tip'е → ловит type/lint/format-поломку комбинации ДО того как она
  отравит следующего воркера (тот ребейзится на этот main). Полный ТЕСТ-сьют — дорогой, его и экономим;
  tsc/lint — дёшев, его держим.
- **Худший случай (редкий, принят): сьют упал, а воркер уже архивирован → fix-forward** — просто подними
  НОВЫЙ трек «почини упавшее» (или переткни воркера, он адресуем по id после архива). Не перегоняй всё
  превентивно ради этого редкого события. Broken main отравляет ветвящихся следующих — потому конец-волны
  гейт всё же делай перед тем как раздать НОВУЮ волну от этого main.

**Source-of-truth доки:** CLAUDE.md · ARCHITECTURE.md (§1 north star, §3 trust) · CONTRIBUTING.md ·
src/README.md (лейеринг). Backlog — **task-manager** (MCP): сначала его `help` + `explain_config`,
правь через MCP, не руками.

**Догфуд:** codemaster MCP жив на этом репо — символьные / типовые / usage-вопросы (и свои, и в
брифах) веди через него, не grep. Собери `feedback` воркеров ДО их архивации — окно одно.

**Инбокс догфуда — твой, и он НЕ второй backlog.** `~/.codemaster/feedback/inbox.md` копится сам;
непротриаженный, он становится конкурирующим списком открытой работы (половина находок живёт только
там) — тот же класс лжи про объём, что два таска на один баг. Инвариант: **инбокс непустой ⇒ есть
непротриаженное**. Читай сам ФАЙЛ, не пересказ воркера (пересказ — тот же релей-вместо-источника, за
который ты гоняешь их), после каждого DONE: конвертнул → перенёс в `archive/` с маппингом
`запись → t-id`; не породило таск → тоже в архив, с причиной.

**Сливай ПО ЗАПИСЯМ, и сверяй счёт механически.** Инбокс ГЛОБАЛЬНЫЙ: туда пишут и внешние агенты из
других репо, поэтому между твоим прошлым сливом и этим там появились записи, о которых тебе никто не
докладывал. Самый частый сбой — слить «по ожиданию»: переносишь то, что воркер ОТЧИТАЛ, а в файле лежит
ещё и чужое. Поэтому: перед сливом `grep -c '^## '`, после — число строк маппинга ОБЯЗАНО сойтись с
числом записей в батче. Не сошлось — ты либо потерял находку, либо написал строку на запись, которой
там нет; архив тогда врёт в обе стороны и выглядит обработанным. Глазами эта сверка не работает —
проверено на себе дважды.

**Внешние находки весят больше, а приходят реже.** Внешний агент (работает в чужом репо, инструмент
только использует) не может перезапустить демон, не может править конфиг в своём репо без побочек и не
видит исходников — его находки про НЕПРИГОДНОСТЬ, а не про неудобство. Внутренние (правят сам
инструмент) докладывают чаще и владеют словарём. Приоритизация по объёму фидбэка систематически
пере-обслуживает внутренних — взвешивай, а не считай.

**Естественные швы декомпозиции:** плагины (`plugins/ts|scss|i18n|schema|react|react-query|…`)
edit-disjoint по домену; `ops/` компонуют плагины поверх (сидят над DAG). Shared-seam (напр.
`ops/intake/resolve-target`) → отдельный трек, ОДИН владелец; зависимые ребейзятся на него.

**Генерируемые файлы регенерируй, не сливай руками:** golden-снапшоты — проектным механизмом
(`UPDATE_GOLDEN`), не 3-way. Env-нюансы: fish не ест inline `VAR=cmd` → `env VAR=… cmd`;
`node --test <файл>`, не директорию.

**main строго прямой → ff-only, по одному** (CLAUDE.md).

**Реальные грабли-классы этого репо:**

- Гипотеза о root-cause часто НЕВЕРНА → отдавай воркеру как «воспроизведи в песочнице», не мандат.
- Рекуррентный класс бага (density-взрыв на `verbosity:full`) = неверный opt-in дефолт → чини
  инверсией на deny-by-default + компайл-страж (`Record<Tag,mode>`: новый тег без классификации =
  tsc-error), не whack-a-mole.
- Вывод выглядит сломанным → воспроизведи CLI one-shot свежим процессом ПРЕЖДЕ чем считать регрессом
  (частый стейл-демон, а не баг кода).

## Классы, оплаченные прошлыми волнами

**Цену своей ошибки протокола платит менеджер, а не воркер.** Сдвинул tip своим коммитом под готовой
веткой — не гоняй воркера на лишний ребейз: `git reset --hard <база воркера>` → `ff-merge` его ветку →
`cherry-pick` свой коммит поверх. Тривиальная интеграция, ровно твоя работа. Ребейз стоит воркеру
контекста и круга, тебе — трёх команд.

**План, ОПРОВЕРГАЮЩИЙ постановку, — норма, а не сбой, и в брифе это пишется прямым текстом.** Твоя
постановка собрана поиском и аналогией, а воркер читает код. Каждое молчаливое выравнивание под неверную
постановку привозит дефект, который никто уже не ищет. В брифе: «не сходится — ДОЛОЖИ, не выравнивай».

**Таблица/перечисление в брифе, составленные ПО АНАЛОГИИ, — гипотеза, а не факт; помечай, что проверено.**
Классический промах: перепись потребителей одного API, где колонка заполнена «как у соседей». Воркер,
доверившийся такой строке, реализует не тот механизм. Пиши «проверено: X; выведено по аналогии: Y —
перепроверь».

**Сравнивай величины одной природы, иначе замер врёт красивее, чем догадка.** In-engine heap ≠
whole-process RSS; `peak memory footprint` ≠ `maximum resident set size`; wall с холодным стартом ≠ без
него; разные адресации одного опа — разные замеры. Неправдоподобная цифра → свежий прогон и явное
называние счётчика, а не объяснение цифры нарративом. Цифра, попавшая в тело таска с неверной единицей,
живёт дольше, чем баг.

**Требуй мутационную проверку, а не «покрыто».** Зелёный тест — заявка. Проверка проверки: сломай то, что
тест якобы стережёт, — он ОБЯЗАН покраснеть; мутант = РЕАЛИСТИЧНЫЙ откат поведения, не удаление поля.
Особый класс — ассерт ОТСУТСТВИЯ маркера на поверхности, у которой нет кодопути к этому маркеру: зелёный
при любом входе. Тель механический: «существует ли хоть один вход, при котором маркер тут появится?».
Удаление вакуумного теста — выигрыш: он снимал ложную заявку на покрытие.

**Общий хелпер: дели ПРОЗУ, структуру — только при совпадении единицы измерения.** Формулировка и
маркер выносятся в один дом (иначе правка = N ручных редактирований). Структура — нет: у неё внутри
дискриминатор («пусто ли по счётчику X»), и в чужой единице он выносит вердикт, которого механизм не
устанавливал. Отказ воркера гнуть чужую форму — правильный ответ; требуй доклад, а не молчаливое
подражание.

**Отказ сильнее ноты.** Если непригодное состояние можно сделать НЕДОСТИЖИМЫМ (упасть выше по течению) —
это лучше, чем объяснять его нотой ниже. Нота объясняет негодный ответ, отказ его не выдаёт. Обратное
тоже правило: завершившийся обход без результата — это ВЕРДИКТ, и отказ там был бы ложью наизнанку.

**Один канал на две аудитории требует проверки на артефакты.** Общий инбокс/лог, куда пишут и агенты, и
ТЕСТЫ, копит записи-пробы; они ломают инвариант «непустой ⇒ есть непротриаженное» и стоят читателю
чтения, чтобы распознать мусор. Любой оп, чей единственный эффект — запись в глобальный путь
пользователя, обязан иметь шов для перенаправления (как у usage-логгера), иначе его собственный тест
загрязняет очередь.

**Проверяй КЛАСС, а не инстанс, и требуй этого от воркера.** «Нашёл и починил в одном месте» — половина
работы; вторая — перечислить остальных потребителей того же шва (одним поиском по API) и сказать, сколько
их и что с ними. Иначе тот же дефект вернётся из соседнего файла через месяц.

**Добор: разделитель — не размер правки, а наличие ДИЗАЙН-решения.** Механическая замена (адопция
вынесенного хелпера, переименование, снятие дубля) — возвращай горячим, без ревью, с точечным прогоном.
Всё, что требует нового поля/семантики/контракта, — отдельный гейт, даже если это «пять строк».
