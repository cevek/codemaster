Контекст и замеры — эпик t-906818.

## 1. Склейка move_file (главное)
Каждый шаг-`move_file` в `transaction` строит свой план (`planMove` → `rewriteImports` по всему дереву под `PlanningOverlay`), ≈2.5 с на шаг на amiro; 30 шагов ≈ 80 с только на планы → таймаут 120 с. Направление: подряд идущие `move_file` шаги транзакции планируются ОДНИМ деревом перемещений (move-tree уже умеет несколько перемещений — перенос каталога), один проход `rewriteImports`. Гейт и capture остаются как есть (один план на цепочку). Решить в плане: где склеивать (transaction-compose vs `move_file` с multi-move аргументом), семантика конфликтов (A→B затем B→C, перенос в путь, освобождённый предыдущим шагом), смешанные цепочки (move_file, rename, move_file).

## 2. Время ожидания в очереди
Запрос, пришедший пока движок workspace занят, ждёт молча: агент отправил 4 транзакции параллельно, последняя ответила через 3 мин 53 с при 58 с работы; usage-лог записал 57.7 с. Минимум: (а) usage-запись несёт время ожидания отдельно от времени работы; (б) ответ, ждавший дольше порога, несёт строку «ждал N с за другими запросами к этому репозиторию — параллельная отправка не ускоряет». Где измерять (мост / daemon / движок) — решить в плане.

## 3. CLI one-shot
`dispose` → `watch/chokidar.ts` `close` занимает 7–9 с на выходе разового CLI (профиль). Разовому процессу не нужно дожидаться закрытия watcher'а (или не нужен watcher вовсе) — решить в плане, не ломая daemon/in-process.

## План

### 1. Склейка подряд идущих move_file — делаю
**Где.** В `transactionOp.run` (`src/ops/transaction.ts`): максимальная серия ПОДРЯД идущих шагов `move_file` планируется одним вызовом нового метода плагина `planMoves(moves[], overlay, deadline)` (`plugins/ts/api.ts` + `plugin.ts`; реализация — `refactor/imports/plan-move.ts`: по парам `findByCurrentPath → проверка dest → moveTo → carrySiblings` на ОДНОМ дереве, затем один `assemblePlan`). `planMove(src, dst)` = `planMoves([одна пара])`, так что standalone `move_file` (`ops/move-file.ts`) и шаг-одиночка не меняются. Шов `planMove`: потребителей два (`ops/move-file.ts`, `ops/refactor-steps.ts`) — оба на одиночной семантике.
Развилка: multi-move аргумент у самого `move_file` — НЕ делаю (новая публичная поверхность; пакетная поверхность уже есть — `transaction`). Склейка внутри `transaction` прозрачна: семантика «шаги по порядку» сохраняется, потому что дерево применяет переносы последовательно по ТЕКУЩИМ путям.

**Семантика.**
- Цепочка A→B, B→C: дерево находит B по текущему пути, узел один → итог A→C (как сегодня даёт TxnCompose).
- Overlay для серии — состояние ДО серии (как у её первого шага сегодня); переносы самой серии попадают в её же `overlayFiles`/`removed` — это семантика одиночного move, обобщённая на N; capture (forward E-g через `prior` + reverse) считается по итоговой раскладке серии, а не пошагово — не хуже сегодняшнего.
- Смешанная цепочка (move, rename, move): rename рвёт серию; получается серия-1 / rename / серия-2, каждая — один шаг TxnCompose.
- Перенос в путь, освобождённый предыдущим шагом (A→B, C→A): сегодня НЕ работает — проверено пробой на текущем коде: dry-run даёт ложную ошибку `Cannot find module './a'` (gate-overlay хоронит origin A при живом содержимом на A), apply отказан; и даже при чистом гейте его отбил бы `collidingDests` (A существует на диске). В одной серии `computeCommitPlan` бросит `unsafe move plan` → честный отказ с индексом шага, ничего не записано. Регрессии нет; ложная ошибка в последовательном пути (смешанные цепочки) — отдельная таска.
- **Атрибуция ошибок**: `planMoves` возвращает при отказе `{ index, message }` — индекс внутри серии; транзакция переводит его в индекс шага (`step i 'move_file' could not be planned: …`), не начало серии. Броски дерева (`moveTo` коллизия, `unsafe move plan`) — так же.
- **Правка `carrySiblings`**: сейчас берёт `initialParent`/`initialName` — для узла, переносимого ВТОРОЙ раз в той же серии, `.module.scss`-сосед (уже уехавший с первым переносом) не найдётся и останется на промежуточном месте. Беру родителя/имя ДО текущего `moveTo` (для одиночного переноса это то же самое — у нетронутого узла initial == current).
- Дедлайн: тело серии — один синхронный блок под `withDeadline`, как сегодня тело шага; опрос дедлайна между шагами в цикле остаётся.
- Op note `transaction`: «подряд идущие move_file планируются одним проходом — держи их смежно» → `node --test test/golden/status.test.ts` с `UPDATE_GOLDEN=1`.

**Доказательство поведения.**
- e2e (`test/e2e/transaction-move-run.test.ts`, новый): оракул — та же раскладка, применённая ПОСЛЕДОВАТЕЛЬНЫМИ standalone `move_file` (apply, `dirtyOk`), итоговые файлы байт-в-байт равны транзакции + холодный `ts.Program` чист. Фикстура: цепочка A→B→C с `.module.scss`-соседом (ловит `carrySiblings`), перенесённый импортёр перенесённой цели, alias/relative импорт. Плюс: смешанная цепочка move, rename, move — чисто; ошибка во втором переносе серии (dest занят) → сообщение называет `step 1`, `git status` чист; swap/вакансия → отказ с индексом, ничего не записано.
- Мутационная проверка: откат `carrySiblings` к initial — красный именно scss-ассерт; индекс серии вместо шага — красный ассерт индекса.
- Замер (копия amiro `/tmp`, in-process, dry-run CLI one-shot): транзакция из 1 / 3 move_file `src/local-api/handlers/presale-*` ДО и ПОСЛЕ, затем один раз 27–30. Baseline снимаю сейчас, до правки.

### 2. Время ожидания в очереди — план ОПРОВЕРГАЕТ постановку, предлагаю вынести
Факты (usage-лог + транскрипт агента `pv2-z-landing`): 4 транзакции отправлены клиентом в 12:51:48 / :52 / :55 / :58; `ts` (старт спана `withCallTelemetry` в мосту, `startMs = clock.now()` на входе хендлера) = 12:51:48.36 / 12:52:54.92 / 12:54:02.95 / 12:54:53.97, и каждый старт = конец предыдущего (±10 мс) = момент выдачи результата клиенту. 4-й ждал 233 с > `BRIDGE_REPLY_DEADLINE_MS` 150 с и не упал — мост его не держал. Значит codemaster получал вызов ТОЛЬКО после ответа на предыдущий: очередь была на стороне клиента (Claude Code), не в `engine.enqueue`. В `src/mcp` нет ни одной tool-аннотации (`readOnlyHint` и т.п.) — клиент считает все инструменты codemaster не-concurrency-safe и сериализует их, включая read-only. Измерять ожидание в мосту/daemon/движке для этого инцидента нечего — 57.7 с в логе верны.
Предложение: в этом треке пункт 2 не делаю. Заводятся таски: (а) tool-аннотации `readOnlyHint` для немутирующих опов (клиент перестанет сериализовать чтения; внутри одного workspace движок всё равно сериализует, выигрыш — между workspace); (б) если нужно мерить ожидание в `engine.enqueue` при нескольких клиентах одного workspace — отдельная таска, пересекается с t-833715 по файлам. Реальное лекарство инцидента — пункт 1: одна транзакция из 30 переносов вместо 5 параллельных.

### 3. CLI one-shot без watcher'а — делаю
`buildOrchestrator(watcher)` в `src/bin.ts`: `status`/`op`/`batch` (разовые) получают `nullWatcher` (`support/watch/seam.ts`), `mcp`/`daemon serve` — chokidar как сейчас. Разовому процессу watcher бесполезен по построению (§3.5: корректность держит read-time проверка) — экономия и на закрытии (7–9 с), и на начальном обходе chokidar. Статус из CLI честно покажет `watcher=off`.
Не покрываю: эскалированный репо из one-shot спавнит `engine-child`, который сам создаёт chokidar (`daemon/engine-child.ts`) — файлы соседа t-833715, отдельная таска.
Доказательство: живой wall-clock `node src/bin.ts op …` на копии amiro до/после. Теста нет: дефект (возврат chokidar в one-shot) тихий, но достижим только проводкой `bin.ts` в субпроцессе, а сигнал — время, не поведение; дешёвой различающей поверхности нет.

### Поправки по plan-ревью (90a4362, BLOCK нет)
- П.2, аргумент заменён: сервер был `mcp --in-process` (моста нет, довод про 150 с reply-deadline пуст). Держит другое: in-process сервер получает I/O-тики на `await runGit` в начале каждого вызова (freshness, `gitLsFiles`) и в apply-фазе (`gitStatus`, prettier, `git mv`); MCP SDK хендлеры не сериализует, `startMs` ставится на входе хендлера — запрос, лежавший в pipe, был бы проштампован ДО конца предыдущего. Факт `ts_n > end_{n-1}` (зазоры 1.0 с / 9 мс / 20 мс) → клиент держал запрос у себя. При нескольких клиентах одного workspace ожидание было бы в `engine.enqueue` — таска t-537226 не гипотетична.
- П.1, атрибуция отказа серии: `unsafe move plan` бросает `computeCommitPlan` после всех `moveTo`, без индекса. Решение: `planMoves` проверяет на входе каждого шага серии, не равен ли его `dest` `source`-у более раннего шага серии (освобождённый путь / swap) → отказ с индексом ЭТОГО шага; оставшиеся броски дерева/commit-плана ловятся внутри `planMoves` и называют диапазон серии (`steps i..j`), как пользовательский отказ `tool:'transaction'`, не `ts-ls`.
- П.3, тест есть: `test/e2e/cli-oneshot-exits.test.ts` уже гоняет реальный `status --root` субпроцессом — добавляю ассерт `watcher=off` (возврат chokidar в one-shot → красный).
- Never-hang серии: внутри тела серии `rewriteImports` не опрашивает дедлайн (как и одиночный шаг сегодня); держится на посылке «серия ≈ один шаг по времени» — замер 18 переносов обязан это подтвердить.
- Вне-скоупные таски заведены: t-469894 (readOnlyHint), t-537226 (ожидание в engine.enqueue), t-191591 (ложная ошибка гейта при переносе в освобождённый путь), t-515246 (chokidar в engine-child).

## Результат

Замер на копии amiro (in-process, CLI one-shot, dry-run; машина под общей нагрузкой load 10–100, поэтому базу и правку гнал попарно, база — detached worktree на 17d1a52):
- transaction из 18 move_file `src/local-api/handlers/presale-v2-*`: ДО — `timeout` на 120 с; ПОСЛЕ — 48 с, typecheck clean; apply на копии — 50 с, 18 переименований, холодный `tsc --noEmit` по результату EXIT 0.
- CPU-профиль ПОСЛЕ, 3 переноса: вся серия `planMoves` 3.6 с (rewriteImports 2.1 с, reverse-capture 0.8 с), `applyRefactorPlan` (гейт) 35 с из 52 с. Время транзакции теперь почти целиком — гейт; на 3 переноса user CPU 64 → 74 с против 64 → 77 с до: остаток роста на перенос живёт в гейте (больше переписанных импортёров → больше файлов в overlay-проверке), а не в плане.
- Хвост выхода CLI (последняя строка stdout → exit): 6.8 с ДО → 0.3 с ПОСЛЕ; `status` на копии 1.8 → 0.8 с. Wall транзакции N=1 под нагрузкой эту разницу не показывает — меряй хвост, не wall.

Факты, вскрытые по ходу:
- Перенос в освобождённый путь (A→B, C→A) на базе не работал и до склейки: ложная ошибка гейта + `collidingDests` → t-191591. Серия рвётся перед шагом, чей dest совпадает с source более раннего шага серии (`moveRunFrom`), и такой шаг планируется новой серией поверх overlay — ровно как отдельные шаги на базе. Для КАТАЛОГОВ (src/a→src/z, src/b→src/a) это рабочий рефакторинг: на базе применялся чисто (TxnCompose собирает пофайлово), и отказ в серии был бы регрессией (поймано bug-ревью); файловый вариант остаётся t-191591.
- `carrySiblings` искал `.module.scss` по месту ПОСТРОЕНИЯ дерева: в последовательном пути это было верно (каждый шаг строил дерево заново из overlay), в серии — нет; теперь ищет по месту до текущего переноса.
- Очередь из п.2 была у клиента (см. поправки к плану), инцидент лечится одной транзакцией вместо пяти параллельных; op note `transaction` это теперь говорит.

Не покрыто: эскалированный (process-mode) движок из one-shot CLI по-прежнему создаёт chokidar в ребёнке — t-515246.
